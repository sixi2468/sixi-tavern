# 段首缩进 与 审核机制说明

## 一、段首缩进

### 现在的规则

- **一行就是一段**：你在正文里换一次行，就是一个新段落；
- 每个段落的**第一行缩进两个字**，且所有段落缩进完全一致（实测每个 `<p>` 的 `text-indent` 都是 33px = 2 × 16.5px 字号）；
- 段落的**第二行起顶格**，这是中文排版的标准做法；
- 引用（以 `>` 开头）不缩进，左侧有朱砂竖线；
- 首段也缩进，不做特殊处理。

![缩进效果](preview/q_indent.jpg)

### 为什么之前看起来"缩进不一样"

旧的实现只在**空行**处分段，单换行被转成 `<br>`。
而 CSS 的 `text-indent` 只作用于"块的第一行"，`<br>` 后面的行属于同一块，
所以**不会缩进**——于是同一篇里有的行缩了、有的没缩。

现在改成"一行一段"，每段都是独立的 `<p>`，缩进自然统一。

### 写作时的建议

- 一个自然段写一行，不要为了排版手动加空格；
- 段与段之间不需要空行（空行会被忽略）；
- 引用他人的话，在行首加 `>`。

## 二、发布后由谁审核

### 纯静态版（你现在用的）

**没有第三方审核人。** 说清楚一点：

- 内容存在**你自己的浏览器**里，没有服务器，也不会上传到任何平台；
- "审核"只发生在你本机：笔记先进「待发布」，然后由**馆主账号**在后台「审核队列」通过；
- 默认开启「发布前检查」时，**6 秒后自动放行**（模拟审核回调）；
- 如果你在设置里把「发布方式」改成手动，笔记会一直停在待发布，直到馆主在后台点「通过」。

所以：**审核人就是你（馆主）**，不是平台、不是云厂商。

### 为什么你看到"审核了很久"

旧版用的是页面里的定时器（`setTimeout` 6 秒）。如果你发布后**切换了页面**，
定时器随页面销毁，那条笔记就永远停在「待发布」——看起来像"审了半天没人管"。

现在改成**读取时结算**：任何页面在读取笔记/评论时，会检查"创建超过 6 秒仍是待发布"的内容并自动放行。
所以离开再回来、换设备重开，都会正常显示为已发布。

### 关闭自动放行后

设置 → 发布方式 → 手动：内容会留在后台队列，必须馆主手动通过。
适合你想逐条过目的阶段。

### 接后端之后（正式运营）

审核会变成两层：

1. **机器审核**：屏蔽词 + 内容安全 API（阿里云/腾讯云/易盾），命中即拦或转人工；
2. **人工审核**：馆主在后台处理队列、举报与申诉。

平台方（Cloudflare、Supabase、云厂商）**不审内容**，他们只提供基础设施；
内容责任在站长。这也是为什么隐私政策、用户协议、举报入口必须留着。

### 用户名也会过屏蔽词

注册和修改资料时，用户名都会先过一遍词库：
命中则直接拒绝，提示「这个名字里有不适合的词，换一个吧」，不会创建账号、也不会改掉原名。
理由很实际——用户名会出现在每条笔记和评论上，是最显眼的展示位。

### 一条内容的时间线（默认设置）

```
点发布 → 状态 pending（前台显示"待发布"）
      → 6 秒内：无可疑内容 → 自动 published
      → 命中屏蔽词：直接 rejected，转为待复核
      → 手动模式：一直 pending，等馆主在后台点通过
```
